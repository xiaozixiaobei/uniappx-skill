# 阶段进入与交接

## 从任务选择入口

| 用户请求 | 合理执行路径 | 结论边界 |
|---|---|---|
| “新建支持 Android/iOS/鸿蒙的项目” | foundation 核对所有目标支持；再按功能进入 API/UI | 工程初始化不等于所有平台已测试 |
| “已有 VDOM 工程只修空状态” | 识别实际模式 → UI → 必要质量验证 | 不顺带迁移或重构其他页面 |
| “接入定位并上传照片” | API → 隐私 → 功能/拒绝/取消验证 | 未核实目标平台能力时不承诺跨端支持 |
| “Vapor 长列表串状态” | UI 检查 key、同文件和循环复用条件 → 质量重现/回归 | 不先引入另一个列表库 |
| “只准备 iOS 提审材料” | store-publish → 查已有包/测试/隐私证据 → 列缺项 | 不默认为上传或最终提交授权 |
| “小米权限审核被拒” | store-publish 读取拒审原文/版本 → privacy/API/构建中实际受影响项 | 不机械重跑所有商店流程 |
| “工具版本升级后继续发布” | 找受影响模式、API/组件、构建/签名及商店规则 → 重验相关项 | 旧报告只在适用条件未变且仍有效时引用 |

简单任务不需要额外创建一份长报告。对用户的自然语言回复包含必要交接信息即可；复杂发布或多平台任务可以把同样的信息落为 Markdown。

## 信息不足时

项目缺失时先给可审阅的实施路径，明确需要哪些工程信息才能改代码；不要臆造源码或声称命令已运行。平台/最低 OS 会改变模式选择时先读取配置；仍不明再询问。

官方来源无法获取时，标明无法核验的具体能力/条款及影响。已取得的版本快照可以用于带日期的解释和准备，但不能据此证明当前商店满足上传要求。新 API 或参数的签名未知时不猜测实现。

目标渠道之间条件不同，分别输出状态；不能用最宽松的渠道结论覆盖其他渠道，也不要以某一家阻塞为由停掉其他独立材料准备。

## 示例交接

```text
适用条件：源码提交 A；Vapor；指定 HBuilderX；Android/iOS；候选包另附哈希。
执行内容：本次仅修复列表复用状态，未涉及签名配置。
证据：Android 当前构建已编译/真机回归，附步骤和日志；iOS 缺设备。
结果与问题：Android 本次回归通过；iOS 必要回归待验证，因此该平台验收阻塞。
下一步：取得 iOS 设备/测试分发后补验；可继续准备渠道材料，但不报整体发布通过。
```

这只是输出结构示例，不是实际执行结果。对真实项目必须替换为可追溯证据，不照抄示例状态。
